# Project review — 2026-08-23

A full read of the repository at `4afa219` (v0.12.2), on `main`, working tree
clean. `pnpm build` and `pnpm test` both pass (60 files, 816 passed, 11
skipped — the skips are the catalogue-gated ones, as designed).

This document is a **findings inventory for delegation**, not a plan. Nothing
was changed. Each item has a stable ID, a severity, an effort estimate, the
files involved, and a concrete suggested action, so items can be handed to
separate agents without re-deriving the analysis.

## How this was produced

Four passes:

1. **Structure** — workspace layout, package manifests, tsconfigs, build and
   release configuration, CI, deployment.
2. **Depth** — every file over ~200 lines read in full; the kernel, schema and
   editor model layers read end to end.
3. **Cross-cutting** — duplication sweeps (repeated type unions, parallel
   renderers, copied helpers), dead exports, type-assertion density, dangling
   documentation references, translation-key coverage, localStorage usage.
4. **Verification** — build/test run, editor bundle built and measured, doc
   references resolved against the filesystem, i18n keys diffed against call
   sites, `dist/` contents inspected.

## Executive summary

The engine layers (`units`, `schema`, `kernel`) are in good shape: the
layering is real and enforced by project references, the invariants in
`AGENTS.md` are actually honoured in the code, and the commenting is
unusually good — most non-obvious decisions carry their reasoning next to
them. The test suite is meaningful rather than decorative.

The pressure is concentrated in four places:

1. **The editor's two god components.** `App.tsx` (1137 lines, one 850-line
   component) and `Canvas.tsx` (1578 lines, one ~1300-line component) have
   absorbed every feature added since milestone 1. Both are still *readable* —
   the comments carry them — but they are where every future change collides.
   This is the single highest-value refactor in the repo.

2. **Node-kind ladders repeated everywhere.** The ten-member node-kind union
   is hand-written in four places, and the "construct a default node of kind
   K / pick its port for direction D" logic exists in at least three
   near-identical nested-ternary chains. Adding an eleventh node kind today
   means finding all of them.

3. **Two half-finished subsystems: i18n and the read-only viewer.** i18n has
   two parallel mechanisms plus a third JSON file, with the English string as
   the lookup key; coverage is incomplete and silently falls back. The course
   viewer duplicates the notebook's renderer rather than sharing it, and has
   already drifted (it silently drops `equation` outputs).

4. **Documentation that outran its own references.** `docs/PLAN.md` and
   `docs/UX-SPEC.md` were deleted in `fbcfe72`; six files and roughly a dozen
   source comments still point at them. `ROADMAP.md` has become a mixed
   backlog-and-changelog with gaps in its own numbering.

Nothing here is alarming. The repo reads like a project that shipped a lot in
a short time and has not yet had its consolidation pass — which is exactly
what this list is for.

## A. Repository, build and tooling

### A1 — No linter or formatter at all — **P2 / M**

`eslint-disable` comments exist in the source but no ESLint is installed and
no config file exists anywhere in the tree.

- `packages/editor/src/canvas/QuickAddMenu.tsx:60,62`
- `packages/editor/src/model/monteCarloPlayback.ts:84`
- `packages/editor/src/tutorial/Tutorial.tsx:100`

Those four comments are inert — they suppress nothing. More importantly,
several findings below (unstable effect dependencies A-la F3, exhaustive-deps
violations, unused vars) are exactly what a linter catches for free.

**Action.** Add ESLint 9 flat config with `typescript-eslint`,
`eslint-plugin-react-hooks`, and `eslint-plugin-jsx-a11y` (that last one
directly serves section H). Add `pnpm lint` to `package.json` and to the CI
and release workflows. Expect a first run to produce real findings; fix or
explicitly disable them per-line with a reason. Prettier is optional — the
codebase is already consistently formatted — but if added, do it as one
mechanical commit so it does not pollute later diffs.

### A2 — `.test.tsx` files are compiled into the shipped `dist/` — **P2 / S**

`packages/editor/tsconfig.json` excludes `src/**/*.test.ts` but **not**
`src/**/*.test.tsx`. Verified: `packages/editor/dist/` currently contains
`canvas/TitleField.test.js`, `model/analysis.test.js`,
`palette/LockedCatalogueSection.test.js`,
`palette/UnlockCatalogueDialog.test.js`, plus their `.d.ts` and source maps.

Consequences: test files are typechecked as application code, `vitest` types
must resolve inside the app project, and test code is emitted as build
output.

`packages/catalogue-author/tsconfig.json` has the identical exclude and is
only unaffected because it happens to have no `.tsx` test yet.

**Action.** Change both excludes to `["src/**/*.test.ts", "src/**/*.test.tsx"]`
(or `"src/**/*.test.*"`). One-line fix in two files; run `pnpm clean && pnpm build`
to clear the stale emit.

### A5 — Editor ships as a single 1.4 MB JS chunk — **P2 / M**

Measured: `build/assets/index-*.js` is **1,397 kB** (465 kB gzip), plus

Three obvious splits, all statically imported today:

plain-text fallback while loading. Add `build.rollupOptions.output.manualChunks`

## C. Cross-cutting architecture

### C1 — The node-kind union is hand-written in four places — **P2 / M**

The ten-member union `'input' | 'formula' | 'output' | 'compare' | 'closure' |
'waypoint' | 'pack' | 'unpack' | 'monteCarloGenerator' | 'monteCarloReceiver'`
appears verbatim in:

- `packages/editor/src/canvas/NodeShell.tsx:26-36` (`Props.kind`)
- `packages/editor/src/help-links.ts:14-24`
- `packages/editor/src/canvas/Canvas.tsx:393-403` (`flowType`'s parameter)
- `packages/editor/src/analytics/analytics.ts:9-20` (as an exported
  `NodeKind`, plus `'frame'`)

`packages/schema/src/document.ts` defines `GraphNode` as a discriminated union
of ten interfaces but **exports no `NodeKind` type**.

Adding an eleventh node kind today requires finding all four and remembering
that the analytics one has an extra member.

**Action.** In `packages/schema/src/document.ts`, add:

```ts
export const NODE_KINDS = ['input', 'formula', /* … */] as const;
export type NodeKind = GraphNode['kind'];
```

then replace all four hand-written unions with imports. `analytics.ts` becomes
`type AnalyticsNodeKind = NodeKind | 'frame'`. Follow the existing
`OUTPUT_KINDS` / `OutputKind` and `VALUE_KINDS` / `ValueKind` pattern in the
same package — this is the third instance of a pattern schema already uses
twice.

### C2 — `AppLocale` is defined twice — **P2 / S**

Two independent definitions of the same type:

- `packages/editor/src/i18n.ts:3-4` — `APP_LOCALES` + `AppLocale`
- `packages/editor/src/model/editorSettings.ts:16` — `export type AppLocale = 'en' | 'nl'`

Consumers are split arbitrarily between the two. From `i18n`:
`model/samples.ts:40`, `canvas/Canvas.tsx:54`. From `editorSettings`:
`model/catalogues.ts:26`, `settings-context.ts:12`,
`settings/SettingsDialog.tsx:26`, `palette/PasswordUnlockForm.tsx:13`,
`palette/LockedCatalogueSection.tsx:11`, `palette/UnlockCatalogueDialog.tsx:14`.

They are structurally identical today, so TypeScript raises nothing — which is
exactly why this will silently diverge the moment a third locale is added to
one and not the other.

**Action.** Keep the `i18n.ts` definition (it has the `APP_LOCALES` array,
which is the useful half). Delete the `editorSettings.ts` one and re-export or
re-import. Six import lines change.

### C3 — Three near-identical node-construction ladders in `Canvas.tsx` — **P1 / L**

This is the largest single duplication in the repository.

`packages/editor/src/canvas/Canvas.tsx` contains:

| Lines | What it does |
| --- | --- |
| 299–331 | Nested ternary building a `GraphNode` from a `QuickAddCandidate` (inside `compatibleQuickAddPort`) |
| 332–340 | Nested ternary picking the port list for that node, given drag direction |
| 1234–1253 | Nested ternary picking an id prefix per choice kind (inside `pickQuickAdd`) |
| 1254–1305 | Nested ternary building a `GraphNode` — **the same construction again**, with `label` added |
| 1306–1325 | Nested ternary picking the port — **the same selection again** |

The two node constructions differ only by whether `label: id` is present. The
two port selections are the same logic expressed with slightly different
formatting. All five are ten-branch chains that a reader has to trace by
counting `?` and `:`.

Beyond the duplication, they encode knowledge that belongs elsewhere: what a
default node of each kind looks like, and which port faces which direction.
`packages/editor/src/model/document.ts:592` already has `defaultOutput(kind)`
doing exactly this for output kinds — the pattern exists, it just was not
extended.

**Action.** Introduce a single registry, in `model/document.ts` beside
`defaultOutput`:

```ts
interface NodeKindSpec {
  readonly idPrefix: string;
  make(id: string, position: Position, document: GraphDocument): GraphNode;
  /** Port a wire dragged *from a source* should land on. */
  readonly targetPort?: string;
  /** Port a wire dragged *from a target* should originate from. */
  readonly sourcePort?: string;
}
const NODE_SPECS: Readonly<Record<QuickAddKind, NodeKindSpec>>;
```

Then all five ladders become table lookups. This removes roughly 130 lines
from `Canvas.tsx`, makes adding a node kind a single-entry change, and gives
`compatibleQuickAddPort` and `pickQuickAdd` a shared source of truth so they
cannot disagree about what a fresh node looks like — a class of bug they can
have today.

### C4 — The table-column connect dance is written three times — **P2 / M**

The "if the target is a table's `NEW_COLUMN` ghost slot, create the column
named after the source node, then check `canConnect` against the *resolved*
column, then connect" sequence appears in `Canvas.tsx` at:

- lines 947–974 (`onConnect`)
- lines 1194–1213 (`wireToExisting`)
- lines 1332–1350 (`pickQuickAdd`)

Each version also re-derives `base` from `nodeLabel(source)` with its own
fallback, and each handles the refusal path independently.

**Action.** Extract one function into `model/document.ts` or a new
`canvas/connect.ts`:

```ts
function connectResolvingColumns(
  document: GraphDocument,
  catalogues: readonly Catalogue[],
  candidate: Edge,
  spectrum: boolean,
): { readonly document: GraphDocument } | { readonly refusal: { edge: Edge; reason: string } };
```

All three call sites collapse to a call plus a refusal branch.

### C5 — `readiness()` is a second implementation of the kernel's wiring rules — **P2 / L**

`packages/editor/src/model/analysis.tsx:169-383`. The docstring says
emphatically that it does not implement a second, laxer kernel — and it is
right about the *evaluation* semantics. But structurally it is a per-node-kind
ladder that duplicates the kernel's knowledge of which ports are required:

- `monteCarloReceiver` needs `MONTE_CARLO_SAMPLE_PORT` (analysis.tsx:210)
- `formula`/`closure` need every input without a default (analysis.tsx:235)
- `compare` needs `VALUE_PORT`, `THRESHOLD_PORT` optional (analysis.tsx:257)
- `waypoint` needs every `in{n}` from `waypointChannelIndices` (analysis.tsx:275)
- `pack` needs none (analysis.tsx:295)
- `unpack` needs `'bundle'` (analysis.tsx:306)
- `output` needs `outputPortNames` minus `THRESHOLD_PORT` (analysis.tsx:343)
- `feasibility` needs its referenced check ids (analysis.tsx:335)

Every one of those facts also lives in `packages/kernel/src/graph.ts` and
`packages/kernel/src/evaluate.ts`. They must agree, and nothing enforces that
they do.

**Action.** Have the kernel export the fact once —
`requiredInputPorts(document, node, formula): readonly string[]` in
`graph.ts`, alongside the existing `outputPortNames` — and let `readiness()`
call it. The state machine (ready / incomplete / blocked) stays in the editor,
which is correct; only the port-requirement table moves. Note that
`outputPortNames` already sets this precedent: it is a kernel export the
editor consumes for exactly this reason.

### C6 — `canConnect` returns a prose string, and the editor parses it — **P2 / M**

`packages/kernel/src/graph.ts:889`:

```ts
export type ConnectionCheck = { ok: true } | { ok: false; reason: string };
```

`packages/editor/src/canvas/Canvas.tsx:618-620` then classifies that string
with a regular expression:

```ts
const unitMismatch =
  (/^cannot connect (?!a )/u.test(reason) || reason.includes('different dimensions')) &&
  !reason.includes('would close a cycle');
```

with a comment explaining that the kernel distinguishes a dimension failure
from a kind failure by writing `"cannot connect a "` in one case and not the
other. Rewording a kernel error message — a `docs:` or `fix:` change nobody
would think to test — silently changes the editor's behaviour: the wrong
refusal UI appears, and the two endpoint nodes stop being highlighted.

**Action.** Add a discriminant:

```ts
export type ConnectionRefusal =
  | 'dimension-mismatch' | 'kind-mismatch' | 'cycle'
  | 'occupied' | 'unknown-port' | 'generic-binding';
export type ConnectionCheck =
  | { ok: true }
  | { ok: false; code: ConnectionRefusal; reason: string };
```

The `reason` string stays for display (`AGENTS.md` is right that a refusal
should be shown in the kernel's own words). The editor switches on `code`.
Roughly a dozen `throw`/return sites in `graph.ts` gain a code; one regex
disappears.

### D5 — Locked-catalogue KDF iteration count is read unbounded — **P2 / S**

**Action.** One `<Dialog>` primitive handling all four concerns, with the four

The `jsx-a11y` plugin from A1 will flag the backdrop `onClick`-on-a-div too
(it wants a keyboard equivalent — which Escape provides).

### F8 — localStorage quota exhaustion fails silently in three places — **P2 / M**

Three stores share the origin's ~5 MB budget and each holds full serialized
documents:

- `io/recentDocuments.ts` — up to **8 complete documents** (`MAX_RECENT = 8`)
- `io/autosave.ts` — one complete document
- `io/catalogueCache.ts` — every loaded catalogue's full text, including an
  unlocked R&M catalogue, which is the large one

Every write is wrapped in a try/catch that discards the error with a comment
saying the feature degrades rather than fails. Individually correct. Together,
the failure mode is: a student with a big catalogue and a few recent documents
quietly loses autosave, with no indication, right up until they need it.

**Action.** In C8's shared storage module, distinguish `QuotaExceededError`
from other failures and surface it once through `pushNotice`. Then make
`recordRecentDocument` evict oldest-first on quota rather than giving up, and
consider capping the total recent-document bytes rather than the count.

The durable fix is IndexedDB for autosave and the catalogue cache (which
`io.ts`'s docstring already claims, per B7) — larger budget, async, no
main-thread stall on a large write.

### F9 — `ConfirmDialog`'s message is untranslated — **P3 / S**

`App.tsx:1124`:

```tsx
message="Discard the current graph? Unsaved changes will be lost."
```

A raw English literal, while the dialog's own buttons go through `t()`.
Similarly, all of `MobileLanding`'s copy (`App.tsx:242-259`), the View menu's
`'Hide palette'` / `'Show palette'` (`App.tsx:798-799`), and every
`pushNotice` string (`App.tsx:618`, `692`, `695`, `708`, `710`, `724`, `741`)
are untranslated interpolated English.

**Action.** Fold into F3's step 3. Worth listing separately because the
interpolated ones (`Unlocked ${name} — ${n} formulas.`) need a different
mechanism than `phrase()` provides — that is the concrete reason the
transitional layer cannot simply be extended.

### F10 — `index.html` has no `lang`, description, or social metadata — **P3 / S**

`packages/editor/index.html` is seven lines. Missing:

- `<html lang="en">` — an accessibility requirement (screen readers pick the
  wrong pronunciation), and this app has a Dutch locale
- `<meta name="description">` — for a publicly deployed, link-shared app
- Open Graph / Twitter card tags — the app's whole distribution model is
  "students open a link", and example links are shared directly
  (`?example=belt-lab`)
- `<noscript>` — a blank page for anyone with JS disabled

`packages/docs-site` gets these from VitePress; the editor and
`catalogue-author` do not.

**Action.** Add them to both app `index.html` files. Set `lang` dynamically
from the stored locale on boot, next to the existing `data-theme` effect
(`App.tsx:542-545`).

## G. Performance

None of these is currently painful — graphs are tens of nodes, as the
architecture assumes. They are listed because they are all in the
per-keystroke path, and the cost scales with document size.

### G1 — The document is fully serialized on every render — **P2 / S**

`App.tsx:324`:

```ts
const isDirty = savedSnapshot === undefined || saveDocument(document) !== savedSnapshot;
```

`saveDocument` walks every node, every edge and every frame, builds a JSON
object and `JSON.stringify`s it with two-space indentation — on **every
render of the root component**, which is every keystroke in a title field,
every hover, every selection change.

**Action.** `const currentText = useMemo(() => saveDocument(document), [document]);`
The document is immutable and replaced wholesale on edit, so the reference
check is exact. One line.

### G2 — Recent documents are re-read and re-parsed on every render — **P2 / S**

`App.tsx:760`:

```ts
const recentDocuments = loadRecentDocuments();
```

Called unconditionally in the render body — a `localStorage.getItem` plus a
`JSON.parse` of up to eight full document texts, on every render. The comment
above it argues correctly that no extra state is needed for *correctness*; it
does not address the cost.

**Action.** `useMemo` keyed on a counter bumped by the three actions that
change the list (save, open, pick a recent). Or move it into the menu-building
function from E1 step 4, so it is only read when the File menu is actually
opened — which is the real fix.

### G3 — The global keyboard effect re-subscribes on every render — **P2 / S**

`App.tsx:594`:

```ts
}, [undo, redo, saveToFile]);
```

All three are arrow functions defined fresh in the component body, so the
dependency array changes identity every render: `removeEventListener` +
`addEventListener` on every keystroke.

`Canvas.tsx:509` has the same shape with `[document, edit, selected, setSelected]`.

**Action.** `useCallback` the three (or read them from a ref), so the effect
subscribes once. This is precisely what `eslint-plugin-react-hooks` from A1
reports.

### G4 — `analyse()` can run the kernel up to 18 times per change — **P2 / M**

`model/analysis.tsx:389-504`. Two retry loops, `RETRIES = 8`, each catching a
`KernelError`, marking the offending node, computing its descendants,
rebuilding a subgraph, and retrying:

- up to 9 `resolveGraph` calls (lines 429–447)
- up to 9 `evaluateDocument` calls (lines 467–487)

Exception-driven control flow over a full graph traversal, memoized only on
`[document, catalogues]` — so any edit to a graph with several broken nodes
pays for all of it.

There is a correctness limit here too: a graph with **nine or more
independently broken nodes** exhausts the retries and falls through to a
single global `message`, losing all the per-node diagnostics the loop was
built to produce. `RETRIES = 8` is an undocumented arbitrary cap on how broken
a student's in-progress graph is allowed to be.

Note the coupling: `descendants()` (line 138) is an O(N·E) fixpoint loop, run
once per retry.

**Action.** The real fix is kernel-side and pairs with C6: have `resolveGraph`
and `evaluateDocument` **collect** diagnostics into a result rather than
throwing on the first one. Then `analyse` is one pass, no cap, and the editor
stops re-running the kernel to discover errors one at a time.

Interim (S): the two retry loops are structurally identical — extract one
`retryDroppingFailures(run, onFailure)` helper. That does not fix the cost but
halves the code and makes the cap visible in one place.

### G5 — `onNodesChange` walks the change list four times — **P2 / S**

`Canvas.tsx:718-844`: one pass to compute `removed`, then `setSelected`,
`setMeasured`, `setRestingMeasured`, and `editLive` each iterate `changes`
again — five traversals, three of which allocate a fresh `Map` copy per call
regardless of whether anything changed. Fires on every drag tick.

`measured` and `restingMeasured` differ only by a `!selected.has(id)` guard
and could be one map plus a derived view.

**Action.** Single pass building the three deltas, then apply. Fold into E3's
`useFlowChanges()` extraction.

### G6 — `document.nodes.find()` inside the edges projection — **P2 / S**

`Canvas.tsx:707`:

```ts
...(document.nodes.find((node) => node.id === edge.from.node)?.kind === 'pack' && …)
```

inside `document.edges.map(…)` — O(nodes × edges) on every projection rebuild.
The same linear `find` by id appears throughout `Canvas.tsx` (lines 111, 113, 683, 931, 1201, 1344) and `model/document.ts`.

**Action.** Build `const nodesById = useMemo(() => new Map(document.nodes.map(n => [n.id, n])), [document.nodes])` once in `Canvas`, and pass it where
needed. A general `nodeIndex(document)` helper in `model/document.ts` would
serve the other call sites.

## I. Testing

### I1 — No interaction tests at all — **P2 / L**

Five `.test.tsx` files use `renderToStaticMarkup` from `react-dom/server`.
There is no jsdom environment, no `@testing-library/react`, no user-event.

So: `Canvas.tsx`, `App.tsx`, `Palette.tsx`, `ValueEditor.tsx`,
`OutputNodeView.tsx`, `Notebook.tsx` and every dialog — roughly 6000 lines
holding most of the app's behavioural risk — have **zero** behavioural
coverage. What is tested is the pure model layer, which is also the layer
least likely to break.

The static-markup approach is a deliberate lightweight choice and it does test
real things (`TitleField`, `ParameterLabel`, `LockedCatalogueSection`). It just
cannot reach interaction.

**Action.** Add `jsdom` + `@testing-library/react` and target the four highest
risk flows, not broad coverage:

1. Connect two nodes with incompatible units → the refusal message appears and
   both endpoints highlight (this exercises C6 and F-class behaviour at once).
2. Edit a value, undo, redo → the document round-trips through `history.ts`.
3. Open a sample with unsaved changes → the confirm dialog gates it.
4. Quick-add from a dropped wire → the node lands and the wire connects
   (directly protects C3's refactor).

Those four would have caught most of the behavioural findings in section F.

### I2 — `CourseMaterialViewer` is an untested shipped surface — **P2 / M**

247 lines, a public route (`?view=course`), no test of any kind. C7 has
already found one drift bug in it (silently dropping `equation` outputs).

**Action.** After C7's extraction, the shared `ResultView` gets the tests and
the viewer needs only a thin one. Before C7, at minimum a static-markup test
per output kind asserting nothing renders empty.

### I3 — `catalogue-author` is nearly untested — **P2 / M**

`validation.ts` has `validation.test.ts`. `draft.ts` (288 lines — the entire
edit model for the authoring app) has none, and neither does any component or
`io/files.ts`.

**Action.** `draft.test.ts` covering add/remove/reorder formula, port editing,
and the round trip through `saveCatalogue`/`loadCatalogue`. That last one is
the valuable case: this app's whole job is producing files the editor must be

### I4 — Untested modules worth covering — **P3 / M**

## J. Product and feature observations

These emerged from reading the code and are not in `ROADMAP.md`. They are
noted for triage, not proposed.

### J1 — Autosave recovery is silent about failure — **P1**

Covered mechanically in D6. Flagged separately here because it is a
*product* defect, not just a technical one: the recovery feature's failure
mode is indistinguishable from "there was nothing to recover", which is the
worst possible presentation for a data-recovery feature.

### J2 — There is no way to see or manage what is stored locally — **P3**

A student's autosave, eight recent documents, cached catalogues (including a
decrypted R&M catalogue), user equations, favourites, tutorial state and eight
preferences all live in localStorage with no UI to inspect or clear them.

For a shared or lab machine, the decrypted catalogue cache in particular is
worth being able to clear deliberately. A "Local data" section in
`SettingsDialog` — what is stored, how much, and a clear button per store —
would be roughly 60 lines and closes a real gap.

`exampleUrl.ts` handles example ids; `?view=course` is handled separately by a
raw `searchParams.get` in `App.tsx:219`. There is no router, which is
correct for this app — but the two URL parameters are handled by two
unrelated mechanisms, and a third will make that a problem.

A tiny `route.ts` reading both parameters into one typed value would keep it
honest without introducing a router.

### J4 — The feedback email address is hardcoded in JSX — **P3**

`App.tsx:1003` — `mailto:thomas.van.riel@gmail.com`. Along with three GitHub
URLs at lines 989, 1008 and 1018. `help-links.ts` exists and already holds
`DOCS_BASE_URL`.

Move all four into `help-links.ts`. Trivial, but it is the difference between
one edit and four when the project gets a project-scoped address.

## What is in good shape

Worth recording, so a consolidation pass does not disturb it:

- **The layering is real.** `packages/units` → `schema` → `kernel` → `nodes` →
  `editor` holds, and `test/project-references.test.ts` proves it by actually
  attempting illegal imports and asserting the build fails. That test is the
  best thing in the repository.
- **The commenting.** Most non-obvious decisions carry their reasoning
  in place — `Canvas.tsx`'s `flowType` explaining React Flow's reserved type
  names, `history.ts` explaining the two edit paths, `analysis.tsx` explaining
  why it is not a second kernel. This is why 1500-line files are still
  navigable, and it is why this review could be this specific.
- **The crypto.** `lockedCatalogue.ts` picks the right primitives for the
  actual threat model, documents why public-key crypto would be wrong here,
  and explains what the auth tag buys. `D5` is a bounds check on an otherwise
  careful boundary.
- **The safety invariants hold.** No `eval`, no `new Function` — and
  `compile.test.ts:86` verifies that by reading its own source. Two
  `dangerouslySetInnerHTML` sites, both KaTeX output, both with escaped
  non-math parts.
- **The kernel tests are substantial.** `evaluate.test.ts` (1711 lines) and
  `graph.test.ts` (738 lines) test behaviour and edge cases, not coverage
  percentage. `AGENTS.md`'s invented-formula rule is followed throughout.
- **`AGENTS.md` itself.** The architecture invariants it states are actually
  honoured in the code — which is rare, and is why deviations were easy to
  spot.
